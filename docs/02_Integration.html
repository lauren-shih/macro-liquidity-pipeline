Spec for downstream consumers of macro_panel_features.parquet. Companion to README (production spec) and Architecture (pipeline overview).

Audience: anyone plugging this pipeline into a Fama-MacBeth panel, a cross-sectional risk-premia test, or an ML return-prediction model.

1. Purpose

The pipeline produces two primary Parquet outputs (plus cftc_tff_panel.parquet, the raw CFTC wide panel whose two FM-registered columns also enter the features parquet). The two are deliberately separated so that the same raw data serves both monitoring and modelling without ever mixing PIT regimes:

File Lag regime Use case
macro_panel_transformed.parquet MON transforms on the un-lagged panel (rolling windows include t) Dashboard / current-state monitoring
macro_panel_features.parquet pit_align (publication-lag shift) + FM transforms: contemporaneous changes (diff / diff_bps / pct1m / yoy) Fama-MacBeth macro RHS / ML-ready macro features (strict PIT)

This document covers only the features parquet — the artifact that merges into a downstream returns panel. (The companion equity repo's executed notebooks consume the PIT panel instead and compute their own monthly transforms — §4.1, executed variant.)

Code blocks in this document are illustrative recipes, not shipped scripts, unless the block names its source file.

4. PIT semantics — recap

The rule in one sentence: a value may appear at index date t only if the public could already know it by t — look-ahead means using a number the world had not yet seen.

Path 1 — standard fixed lag. Each series shifts forward by its publication lag (config.Indicator.lag is the single source of truth; main.py builds the lag map and passes it to pit_safe.pit_align()), then lands on a business-day grid with forward-fill. Concrete timeline (FINRA, lag=25): the September margin-debt value carries data_date = 2024-09-30 → FINRA publishes ≈ Oct 25 → the value first appears at late-October index rows, never at 2024-09-30 — a model predicting October returns with margin debt sees only what was public at the time.

Path 2 — vintage first release. The 8 revision-prone series (CPI / M2 / Core PCE + the NFCI family ×5) skip fixed lags entirely: the first-release value enters at its true effective_date (ALFRED realtime_start). Concrete timeline (CPI): the June figure is first published by the BLS in mid-July → the panel carries that first print at its actual mid-July release date, and later revisions never overwrite it. See §10.

Then, transforms. apply_transforms(mode='fm') computes contemporaneous changes (diff / diff_bps / pct1m / yoy) on the PIT-aligned panel — alignment first, transforms second, so no change is computed across un-shifted dates.

The transformed (un-lagged MON panel) shows the same values at their original reference dates. The two files must never be mixed.

4.1 Cross-market timezone adjustment (US → TW use) ⭐

The PIT semantics in §4 are canonically US-perspective — pit_align() shifts each US series forward by its US-side publication lag, so the shifted index represents "earliest date a US trader at NY close would have known the value."

For Taiwan-equity Fama-MacBeth use, an additional 1-business-day shift is required because TW trading hours close (~05:30 UTC) systematically precede the same-calendar-day US morning publication window (~12:00–14:00 UTC).

Why the extra day?

Concrete example — SOFR for original date 2024-08-28: - Config: publication_lag = 1 → pit_align() shifts the value to index 2024-08-29 - This index represents "available at NY close 2024-08-29" - NY Fed publication time: 2024-08-29 08:00 ET = 12:00 UTC = Taipei 20:00 on 2024-08-29 - TW close on 2024-08-29: 05:30 UTC = Taipei 13:30 → SOFR for 2024-08-28 is not yet published - TW close on 2024-08-30 (next business day): 05:30 UTC → SOFR for 2024-08-28 is published (Taipei yesterday evening)

So for a TW trader at TW close on date t, the latest available US daily series is the pit-aligned value at index (t − 1 business day), not (t).

Scope of impact

Series cadence US-side lag Extra TW shift Net leak if not corrected
Daily (SOFR, DGS10, VIX, DEXTAUS, OAS, SP500) 1 +1 BDay 1 day leak at every month-end
Weekly (WALCL, WDTGAL) 1 +1 BDay (negligible) ~1/5 of pub cycle
Monthly (FINRA; CPI / M2 / PCE via vintage first-release, §10) 25–58 +1 BDay (negligible) <10% of pub lag

The daily-series row is the only one that matters for monthly Fama-MacBeth, but it affects every month-end factor value computed from daily inputs (SOFR-EFFR spread, HY OAS diff, FX return, VIX level, SPX return, etc).

Implementation

Apply the shift at merge time in the equity panel-build code — do not modify pit_safe.py (which stays canonical US-perspective for general consumers):

# Load US-perspective features
macro = pd.read_parquet('output/macro_panel_features.parquet')

# Cross-market shift: TW trader at TW close on date t can use US values
# whose pit-aligned index is at (t − 1 business day)
macro.index = macro.index + pd.tseries.offsets.BDay(1)

# NOW resample to month-end — the shift propagates correctly through .last()
macro_m = macro.resample('ME').last()

After this shift, macro_m.loc['2024-08-30'] returns values that were definitely published by NY close on 2024-08-29 — well before TW close on 2024-08-30. Zero look-ahead from TW perspective.

Why the shift is not built into pit_safe.py?

Three reasons: 1. Layer separation: pit_safe.py handles series-level publication lag (US-side); cross-market timing is a merge-time concern. Keeping them separate makes each layer auditable in isolation. 2. Consumer flexibility: a US-side consumer of the features parquet should not get an extra +1 day shift built in. 3. Generality: the +1 BDay rule applies only when LHS is TW equities. If LHS were US equities, no shift is needed; if LHS were European equities, the shift magnitude/direction would differ (timezone-specific).

The +1 BDay shift lives at the merge-code level and is documented here for whoever rebuilds the equity panel.

Executed variant (companion equity repo). The companion repo's notebooks do not consume the daily features parquet; they read macro_panel_pit.parquet (PIT levels) and perform an explicit month-end as-of join — merge_asof(direction='backward', allow_exact_matches=False) — computing monthly changes downstream. The strict inequality means "take the last value available before month-end, excluding month-end itself": the 2024-08-30 row joins the last value dated ≤ 2024-08-29. Because a Taiwan close always precedes a same-day US release, that inequality alone guarantees zero look-ahead — no +1 BDay needed on that route. The recipe above serves consumers who take the daily features parquet directly.

Design rationale — summary

How the pipeline handles the US–TW timezone offset, in one paragraph:

Our pit_safe.py is canonically US-perspective — each US series is shifted by its US-side publication lag, producing 'available at NY close' semantics. For the TW equity Fama-MacBeth panel, we apply an additional +1 business day shift at merge time, since TW close (05:30 UTC) precedes US morning publication by ~7-8 hours. This is layer-separated by design: series-level PIT in pit_safe, cross-market timing at merge. After the shift, every month-end factor value is provably knowable at the corresponding TW close.

5. Sparsity & resampling

Non-null counts in the parquet are the raw non-nulls — i.e. the number of dates on which the source actually changed. After PIT shift but before any ffill in downstream code, monthly and quarterly series will read NaN on most business days.

Downstream pattern for monthly Fama-MacBeth:

import pandas as pd

# 1. Read features (PIT-aligned)
macro = pd.read_parquet('output/macro_panel_features.parquet')

# 2. Pick columns of interest
cols = [
    'SOFR', 'EFFR',                            # repo spread inputs
    'BAMLH0A0HYM2', 'BAMLH0A0HYM2_diff_bps',   # HY credit (FM form: Δ bps)
    'NFCILEVERAGE',                            # leverage gauge
    'WALCL', 'WDTGAL', 'RRPONTSYD',            # Net Liquidity components
    'DEXTAUS', 'DEXTAUS_pct1m',                # FX
]
macro = macro[cols]

# 3. Forward-fill the sparse series onto the business-day grid
#    (safe because the PIT shift has already moved each value to its
#    first-known date; ffill only propagates a known value forward)
macro = macro.ffill()

# 4. Build derived features at the DAILY level first
macro['SOFR_EFFR_bps']    = (macro['SOFR'] - macro['EFFR']) * 100
macro['NET_LIQUIDITY']    = macro['WALCL'] - macro['WDTGAL'] - macro['RRPONTSYD']

# 5a. Cross-market shift (US → TW): see §4.1
#     This is the difference between US-perspective and TW-perspective PIT.
macro.index = macro.index + pd.tseries.offsets.BDay(1)

# 5b. Resample to month-end
macro_m = macro.resample('ME').last()

# 6. Compute month-over-month CHANGES for level series → factor-style returns
macro_m['HY_OAS_d_bps']       = macro_m['BAMLH0A0HYM2'].diff() * 100
macro_m['NET_LIQ_d_pct']      = macro_m['NET_LIQUIDITY'].pct_change() * 100
macro_m['NFCI_LEV_d']         = macro_m['NFCILEVERAGE'].diff()
# DEXTAUS_pct1m is already a 21-bday return — at month-end it is ~MoM FX return
macro_m['FX_pct1m']           = macro_m['DEXTAUS_pct1m']

# 7. Merge to Taiwan equity monthly panel on month-end key
#    (equity_panel: MultiIndex [date, stock_id], columns include r_next, r_excess, etc.)
panel = equity_panel.join(macro_m, on='date', how='inner')

Calendar choice: Use pd.tseries.offsets.MonthEnd (i.e. 'ME' frequency string) so both US-side macro and the TW equity panel align to the same Friday/last-business-day. If TWSE has a holiday that NYSE doesn't (or vice versa), step (3) ffill before resample handles it without leaking.

Boundary rule (US-perspective): A factor value at month-end t is used to predict equity returns over month t+1. The features parquet's PIT shift guarantees the value at t is something a trader at NY close on date t would have known.

Boundary rule (TW-perspective, see §4.1): With the additional +1 BDay shift applied at merge time, the value at t is something a trader at TW close on date t would have known — strictly correct for Taiwan equity panels.

6. FX factor specifics (DEXTAUS)

The FX block is central to the Macro RHS pricing test — the liquidity-injections → forward-equity-risk-premia hypothesis needs an FX transmission channel. DEXTAUS is also the only series whose configured lag is set earlier than its upstream archiving cadence — information time T+1 against the H.10 weekly median of T+5, the +4 in the residuals table, by design. Every other divergence runs the opposite way, a −1 strictly-prior conservative day, while DTWEXEMEGS is configured at 5, matching the cadence, gap 0. Together with the λ_FX sign convention driving FM interpretation, the series gets a dedicated section.

Column meanings: - DEXTAUS — raw spot rate, TWD per USD (so rising = TWD weakening). FRED H.10 NY 12pm noon buying rate; config lag T+1 by information time — a traded spot is market-observable on its date; H.10's weekly posting is archival (see §10.1). - DEXTAUS_pct1m — 21-business-day percentage change. This is the FX return for use as an RHS factor.

Sign convention for interpretation:

DEXTAUS_pct1m TWD direction Foreign capital flow proxy
> 0 TWD weakening Outflow / risk-off
< 0 TWD strengthening Inflow / risk-on

For Fama-MacBeth, DEXTAUS_pct1m works directly as an RHS factor. Expected sign on cross-sectional λ_FX is negative if TWD strengthening predicts higher next-month Taiwan equity returns (the "carry / inflow" interpretation), but a hypothesis test does not assume the sign — let the data speak.

Important nuance — the 21-bday window of pct_change_1m does not align perfectly to calendar months. At month-end, the value reflects the FX return from ~21 bdays ago, which is approximately one calendar month but not exactly. For tighter alignment, recompute manually:

fx_monthly = macro_m['DEXTAUS'].pct_change() * 100   # exact MoM at month-end

For the monthly panel, prefer this recomputed version over the precomputed DEXTAUS_pct1m to keep the time alignment crisp.

7. Data provenance & current limitations

7.1 Credit OAS deep history — provenance & reproducibility

The five ICE BofA OAS series are distributed on FRED under ICE licensing; since April 2026 the live API returns only a rolling ~3-year window for them. The deep history in this repo's cache comes from the official FRED full-history download, obtained while the full history was still publicly distributed, and is programmatically spliced with live increments:

  • fred_loader.fetch_one's full path uses accumulate-and-merge (combine_first): fresh values win where present; cached deep history survives wherever the API window has rolled off. No hardcoded protection list — self-healing by construction.
  • main.py's build-time coverage guard refuses to write the features parquet if any protected deep-history series falls below its coverage floor (first-valid-date / non-NaN count), so a washed splice can never silently reach consumers.

Net effect for consumers: the output parquet carries the full OAS history end-to-end; nothing was hand-assembled, and the splice is reproducible from the archived official download + the live API.

7.2 BGCR (not distributed by FRED)

BGCR — the NY Fed's broad general-collateral repo benchmark — is absent because FRED does not distribute the series. Tri-party GC repo conditions are covered by TGCRRATE and SOFR (Block 1).

7.3 SP500 is a price index (reference only)

The FRED SP500 series is a price index. It is carried for regime context / conditioning, not as an equity-return benchmark — pricing tests should use a total-return index on the equity side.

7.4 CFTC holiday-calendar nuance

CFTC TFF release-date shifting uses USFederalHolidayCalendar, not an NYSE-specific calendar. The difference is minimal at weekly cadence; documented for completeness.

8. End-to-end usage example (Macro RHS pre-flight)

Same semantics as the companion repo's executed variant (§4.1).

import pandas as pd
import statsmodels.api as sm

# === A. Load PIT-aligned macro features ===
macro = pd.read_parquet('output/macro_panel_features.parquet')

# === B. Build clean monthly macro factor panel ===
keep = ['SOFR', 'EFFR', 'BAMLH0A0HYM2', 'NFCILEVERAGE',
        'WALCL', 'WDTGAL', 'RRPONTSYD', 'DEXTAUS']
macro = macro[keep].ffill()

macro['SOFR_EFFR_bps']  = (macro['SOFR'] - macro['EFFR']) * 100
macro['NET_LIQUIDITY']  = macro['WALCL'] - macro['WDTGAL'] - macro['RRPONTSYD']

# Cross-market PIT shift for TW panel (see §4.1)
macro.index = macro.index + pd.tseries.offsets.BDay(1)

macro_m = macro.resample('ME').last()

factor_panel = pd.DataFrame(index=macro_m.index)
factor_panel['REPO_SPREAD']    = macro_m['SOFR_EFFR_bps']
factor_panel['HY_OAS_d_bps']   = macro_m['BAMLH0A0HYM2'].diff() * 100
factor_panel['NFCI_LEV_d']     = macro_m['NFCILEVERAGE'].diff()
factor_panel['NET_LIQ_d_pct']  = macro_m['NET_LIQUIDITY'].pct_change() * 100
factor_panel['FX_pct1m']       = macro_m['DEXTAUS'].pct_change() * 100

# === C. Sanity-check no look-ahead at sample boundary ===
# A factor value dated 2025-01-31 should only use info knowable by NY close 2025-01-31.
print(factor_panel.loc['2025-01-31'])

# === D. Pre-flight collinearity check (VIF) before Fama-MacBeth ===
from statsmodels.stats.outliers_influence import variance_inflation_factor

X = factor_panel.dropna()
X_const = sm.add_constant(X)
vif = pd.Series(
    [variance_inflation_factor(X_const.values, i) for i in range(X_const.shape[1])],
    index=X_const.columns,
)
print(vif)

VIF > 10 on any pair would suggest dropping or orthogonalizing. The expected concern is REPO_SPREAD vs NFCI_LEV_d (both pick up funding stress); HY_OAS_d vs NET_LIQ_d (liquidity drives credit — spreads widen when Net Liquidity contracts, so monthly changes are expected to correlate negatively). Document whichever is dropped in the methodology write-up — the companion repo's selection methodology is the executed version of exactly this check.

9. Forward notes for consumers

  • No prebuilt Net-Liquidity column. The parquet ships the three components separately (WALCL / WDTGAL / RRPONTSYD) because unit conventions for ON-RRP and the TGA differ across shops — composing downstream keeps the exact definition auditable; the one-liner is in §8.
  • Cite official release calendars, not config constants. config lags are engineering calibrations — validated against the ALFRED sweep for daily/weekly series, replaced by the first-release route for monthly macro (§10). A formal write-up should reference the BLS / Fed calendars.
  • No z-scores in the parquet (composite or per-series). If a windowed feature is needed — e.g. a Net-Liquidity z-score — compute it downstream with rolling_zscore(NET_LIQUIDITY, 252, lag=1); it enters config only if it becomes a standing RHS factor.
  • CFTC TFF is registered. Leveraged-fund net UST positioning (TFF_2Y/10Y_LEVERAGED) rides the same features route as the FRED series and doubles as the dealer balance-sheet-capacity narrative.

10. Vintage path (first-release) — design & evidence

10.1 Scope & one-cut rule

Vintage treatment is selective by design, not blanket.

What the lag field means. It encodes information time — when a value becomes knowable. Market-priced series are knowable on their market date (config carries a 0–1 day strictly-prior buffer); calculated releases are knowable at their publication time; revision-prone statistical releases fit no fixed lag at all and take the vintage route instead.

Empirical basis (ALFRED sweep). The sweep confirms the fixed-lag registry against this standard: publication-timed series show residuals of ≈ 0–1 day (per-series table below). The real gap sits at revision-prone levels × long publication delays — CPI ≈ 42 days, M2 ≈ 55, PCEPILFE ≈ 58 (medians over 49 releases each). No fixed lag can represent those delays, so the three monthly series take the first-release route.

Why the NFCI family joins them. The criterion is revision risk, not delay: the Chicago Fed restates history retroactively — first-release vs latest-vintage ANFCI diverges by 0.468 (material; archived 2026-05 calibration, not shipped, reproducible from the vintage loader + the live ALFRED API). The sweep csv's vintage_now column marks only the three monthly series; NFCI's vintage assignment rests on revision risk rather than measured availability delay (listed NO-recent-period).

The control case (DTWEXEMEGS). It revises frequently in ALFRED (index re-weighting; 87.8% of vintages) yet its lag is calibrated exactly (config = 5, gap 0), so it stays on the fixed-lag path as Tier-2 robustness — the selectivity criterion is divergence, not revision per se.

One-cut rule. The vintage / fixed split is decided once in the registry — revision-prone series (the 8 above) take the first-release route regardless of consumer; every other series, including the FM-reach ones, keeps its calibrated standard lag (29 FRED series). Blanket vintage would add cache footprint with zero PIT benefit on the already-calibrated daily/weekly set.

Per-series calibration residuals (ALFRED sweep) — the underlying series feeding the factor-selection candidates. Gap = ALFRED median first-appearance − configured lag (negative = conservative: the config treats data as available later than it actually is, zero look-ahead by construction; positive = aggressive). Configured lags are read from config.Indicator.lag, the single source the pipeline itself uses:

10.3 Mechanics & consumer impact

FRED-native output_type=4 (Initial Release Only) returns one first-release row per data date with its true realtime_start. pit_safe_vintage.extract_first_release (explicit stable sort + drop_duplicates, PIT invariant asserted) and pit_align_vintage (merge_asof(direction='backward')) align these onto the business-day grid as levels. All FM transforms are then computed by the same apply_transforms(mode='fm') as standard series — single transform source.

Consumer impact: none. Vintage series appear in macro_panel_features.parquet as ordinary columns (level + declared transforms) — no special code path is needed downstream. Module details live in the docstrings of src/fred_loader_vintage.py and src/pit_safe_vintage.py.

11. Downstream: factor selection & DB warehouse

11.1 Which columns enter a pricing panel?

This spec defines mechanical consumption of the parquet; it deliberately does not decide which indicators belong in a priced RHS panel. That is a selection methodology question — layered screening (economic thesis → univariate IC → pairwise collinearity), with selection kept separate from estimation for out-of-sample validity. The executed variant for the Taiwan cross-section lives in Macro_Factor_Selection_Methodology in the companion factor-model repo, alongside the notebooks that consume the pipeline's PIT panel (macro_panel_pit.parquet) via a strict as-of join — see §4.1, executed variant.

11.2 DB warehouse context (planned ingest)

A planned ingest layer lands both domains in one SQLite warehouse (quant_research, SQLite), so factor selection and Fama-MacBeth can pull LHS + RHS with a single as-of SQL JOIN:

quant_research (SQLite)
├── tej_* (7 tables):              individual-stock daily/monthly, IDs, financials
├── tej_universe_returns_monthly:  2 LHS labels (equal_weight / cap_weight)
│                                   ← factor-selection notebook (separate TEJ flow)
├── macro_panel (long-format):     40 indicators × {level + declared transforms}
│                                   ← collect_macro_data.ipynb (this pipeline)
└── macro_panel_indicators:        metadata (block, pit_path, publication_lag)

As-of JOIN pattern:

SELECT u.year_month, u.monthly_return, m.value AS rhs_factor
FROM tej_universe_returns_monthly u
LEFT JOIN macro_panel m
    ON m.series_id = 'BAMLH0A0HYM2' AND m.transform = 'diff_bps'
    AND m.release_date <= date(u.year_month || '-01')  -- as-of guard
WHERE u.universe_label = 'equal_weight'

SSoT discipline: macro_panel_features.parquet remains the production SSoT; the DB is a downstream consumer — schema change / migration / corruption cannot affect the pipeline's standalone testability. Full spec: Macro_DB_Ingest_Design.

11.3 CFTC TFF release_date — verified ground truth

The DB ingest layer computes release_date per 3 source groups; the CFTC TFF group needs explicit ground truth verification (cftc_loader.py tracks Tuesday data_date; release_date is computed at ingest).

Verified from CFTC.gov + secondary sources:

Item Verified ground truth
Data date Tuesday (weekly open-interest as-of date)
Release date Friday 3:30 PM Eastern Time (weekly)
Standard lag 3 business days (Tue → Fri)
Holiday rule Monday US federal holiday → data shifts Tue → Wed; Friday holiday → release shifts to Thursday

Implementation (in collect_macro_data.ipynb Cell 5):

from pandas.tseries.holiday import USFederalHolidayCalendar
from pandas.tseries.offsets import CustomBusinessDay

us_bday = CustomBusinessDay(calendar=USFederalHolidayCalendar())

def cftc_tff_release_date(data_date_tuesday):
    return data_date_tuesday + 3 * us_bday
