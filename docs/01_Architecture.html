📖 Reading guide:
  • config.py is the single source of truth: every module imports it; adding or removing an indicator touches one file. VINTAGE_SERIES decides who takes the ALFRED first-release route.
  • transformations.py is invoked twice (left mode='mon', right mode='fm') — one implementation, two outputs.
  • Dual PIT path on the feature branch: 17 FM-reach series take the standard fixed lag (calibrated against an ALFRED sweep: median real lag of 0–1 day for rates, credit and balance-sheet series; the two FX series post weekly at ≈5 days — Integration §10.1); the 8 revision-prone series take true first-release effective dates.
  • Selective, not blanket (one-cut rule): only series whose measured first-release gap is material go vintage — an empirical cost-benefit cut, not an assumption.
  • Two parquets coexist by design: macro_panel_transformed (un-lagged, dashboards show today) vs macro_panel_features (strict PIT for models) — Part D.
  • main.py is an overlay, not a middle layer — it orchestrates call order and owns no computation.

Part C · The 12 core modules — why each exists & how they connect

Each card covers only the reason to exist and the upstream / downstream interface — internal logic lives in the module docstrings. Utility scripts (the fetch_long_* deep-history prefetchers, adf_check.py, alfred_sweep.py) are catalogued in the README repository map. Purple cards are the ALFRED first-release path (8 VINTAGE_SERIES).

[1]config.pyindicator registry — single source of truth

Why: if series ids, transform lists, sources and lags were scattered across loaders / transforms / dashboards, adding an indicator would be painful and "fetched but never transformed" bugs would slip in silently. The frozen dataclass registry centralizes all metadata; validate_config() runs at import (fail at load).

Upnone (definition layer)Downby_source('FRED') feeds loaders; apply_transforms reads mon/fm lists; the lag map feeds pit_align.
[2]fred_loader.pyFRED fetch + local cache (standard path, 29 series)

Why: FRED quotas are real and the API occasionally fails. Cache-first three-path logic (fresh → read / stale → incremental / missing → full) plus parallel fetch with per-series failure isolation. The full-fetch path uses accumulate-and-merge (combine_first): fresh values win, cached deep history survives — the OAS deep-history splice is protected by construction, no hardcoded list (its pre-2023 history is no longer retrievable from the live API after ICE's 2026-04 redistribution change — overwrite it and it is gone; provenance in Integration §7.1).

Upconfig.py ids, FRED_API_KEYDowncache/*.parquet (one per series)
[3]fred_loader_vintage.pyALFRED first-release fetch (8 series)

Why: fixed lags approximate monthly macro badly — measured first-release lag is ~42 / 55 / 58 days for CPI / M2 / Core PCE (the registry carries lag=None for all three and routes them via ALFRED), and the NFCI family is retroactively revised. Uses FRED-native output_type=4 (Initial Release Only) to avoid the ALFRED 100k-row truncation that get_series_all_releases hits on weekly revised series. Scope is selective: only the 8 series where the gap is material (one-cut rule).

Upconfig.VINTAGE_SERIESDowncache_vintage/*.parquet (realtime_start, date, value)
[4]cftc_loader.pyCFTC TFF fetch (self-built REST client)

Why: FRED does not carry the CFTC Traders-in-Financial-Futures detail (leveraged-fund / asset-manager / dealer net positioning). CFTC has no official Python SDK, so this is a direct Socrata REST client. The column map is verified against the live Socrata schema (naming is inconsistent upstream: some groups carry an _all suffix, some do not). Leveraged-fund UST net shorts are the core basis-trade monitoring input.

[5]finra_loader.pyFINRA margin debt (monthly)

Why: retail / levered-equity positioning proxy. Monthly cadence, publication lag ≈ 25 days; the margin-to-M2 composites for the leverage panel are assembled downstream from its level.

[6]pit_safe.pystandard fixed-lag PIT layer

Why: FRED stores values at the reference date, but reality only reveals them at the publication date. pit_align shifts each column's index by its publication lag and re-grids to business days. The lag map comes from config.Indicator.lag (17 FM-reach series; missing lag → hard fail). Daily/weekly lags were validated against an ALFRED sweep (median real lag of 0–1 day for rates, credit and balance-sheet series; the two FX series post weekly at ≈5 days).

Upraw wide panel columns (FM-reach)Downmacro_panel_pit.parquet
[7]pit_safe_vintage.pyfirst-release alignment (3 layers)

Why: replace the fixed-lag approximation with the true first-release effective_date for the 8 revision-prone series. L1 extract_first_release (explicit stable sort + dedup — a defense against silent revision leakage); L2 pit_align_vintage (merge_asof(direction='backward'), the pandas as-of join idiom); L3 outputs first-release levels only — every FM transform is computed downstream by the same apply_transforms, so vintage and standard series share one transform implementation.

Upcache_vintage/*.parquetDownlevels merged into macro_panel_pit.parquet
[8]transformations.pyfeature engineering layer

Why: raw levels are not cross-comparable (a policy rate in %, an OAS in bps, an index level). Z-scores / YoY / changes convert levels into unit-free signals. Two design keys: mode='mon' vs mode='fm' select per-series transform lists from config; and YoY is frequency-aware — series are resampled to native frequency before pct_change, so a forward-filled daily grid can never silently corrupt a monthly YoY.

Part D · Dual-output design (the core insight)

The pipeline runs two independent look-ahead defenses — and they address different failure modes.

Look-ahead source · Type 1
"When could the data actually be seen?"

Problem: timeline misalignment (publication lag) — the reference date ≠ the knowable date.

Example: the September CPI print goes public in mid-October (true first-release lag ≈ 42 days median).

Defense (dual path): pit_safe.apply_publication_lag for the 17 FM-reach standard series (lags validated by an ALFRED sweep); pit_safe_vintage first-release alignment for the 8 revision-prone series (true ALFRED effective dates).

Look-ahead source · Type 2
"Does the statistic peek at t itself?"

Problem: a rolling window that includes t — a z-score whose mean covers [t−251, t] cannot serve as a next-period predictor.

Example: x.rolling(252).mean() used to predict t+1 returns is optimistically biased.

Defense: mode='fm' ships contemporaneous changes only (diff / diff_bps / pct1m / yoy) — no windowed statistic enters the feature matrix. Z-scores exist only on the monitoring layer, computed at lag=0 (window includes t — fine for display; see the table below). The same z implementations carry a lag ≥ 1 switch, so any future windowed feature would be strict-past by the same code path.

Why two separate outputs?

Output parquetLook-ahead defensesUse
macro_panel_transformednone — deliberatelyDashboards showing today's z-score (the viewer's clock is today; nothing is leaked)
macro_panel_featuresType 1 ✓ + Type 2 ✓Factor-model RHS / ML-ready macro features (strict PIT)

What breaks with only one output

transformed only (no PIT)
In-sample R² looks great, out-of-sample collapses — the model has been fed values that were not public yet.
features only (strict PIT)
The dashboard permanently lags reality — today's stress never shows up until its publication lag has passed.
🎯 Why the distinction matters: most look-ahead discussions stop at Type 2 (strict-past windows). Type 1 — publication timing — is the quieter leak, and it needs its own mechanism because no amount of window shifting fixes an index that sits at the wrong date. This pipeline treats the two as separate defenses with separate code paths.
